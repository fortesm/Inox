Overview

Inox is a strongly typed, compiled programming language for high-integrity software. It is designed around explicit syntax, strong static typing, predictable semantics, composition-first design, and LLVM-oriented compilation.

Inox is post-object-oriented: it does not use classes, inheritance trees, Java-style interfaces, duck typing, or mixins as its foundation. The language direction is based on structs as data, associated methods as behavior, composition over inheritance, explicit mutability, and future contracts/protocols/behaviors for statically checked capabilities.

This is Inox 0.2.0, pre-alpha. The language and its compiler share one version, written MAJOR.MINOR.RELEASE.BUILD: inox --version prints, for example, inox 0.2.0.206 pre-alpha. MAJOR is a generation of the language, MINOR adds features (before 1.0 it may still change the language), RELEASE fixes without new features, and BUILD is set automatically by every build (the number of commits compiled). (Numbers such as "canon revision 3.61" name entries of the decision log in openspec/specs/constitution/revisions.md; they are not versions.) The law of the language is the constitution, openspec/specs/constitution/spec.md; this manual derives from it. The current compiler supports a restricted executable subset, textual LLVM IR emission, a Clang-backed native build/run path, regression tests, standard-library discovery, and prebuilt release packages for Windows and Linux.

Quick start: Windows prebuilt package

Download the latest Windows package:

https://github.com/fortesm/Inox/releases/latest/download/inox-windows-x64.zip

Expand-Archive .\inox-windows-x64.zip -DestinationPath C:\Tools
cd C:\Tools\inox-windows-x64

Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.\set-inox-env.ps1

inox .\examples\hello.inox
inox --emit-llvm .\examples\put-output-basic.inox

The setup script configures PATH, INOX_STDLIB, and INOX_OUTPUT_DIR for the current PowerShell session.

Compiler commands

inox build file.inox       build the program; prints the executable path
inox check file.inox       parse and check the program

Standard library discovery and output directory

The standard library has Std.System (the prelude, always available, formerly Std.Core), Std.IO, Std.Math, Std.Errors (the exception types), Std.Debug and the pairs Std.Files / Std.IOUtils and Std.Strings / Std.StrUtils. Modules come in pairs: Std.X holds a subject's types and fundamental operations, and Std.XUtils the conveniences built on them (using Std.XUtils also gives everything of Std.X). Planned: Std.DateTime / Std.DateUtils, and Std.SystemUtils for system functions.

Use Std.Debug gives Assert(Condition) and Assert(Condition, Message). When the condition is false the program stops at once, like an overflow: no handler catches it and no ensure runs. Assert is never compiled out.

Use Std.Debug

Average(Total Integer, Count Integer) Integer :
    Assert(Count > 0, "Count must be positive")
    Return Total div Count
;
== Average(10, 0) stops with:
== Inox runtime error: assertion failed: Count must be positive

The compiler searches the standard library in this order:

  1. INOX_STDLIB, when set.
  2. stdlib/ next to the release package root when the executable is under bin/.
  3. stdlib/ next to the executable.
  4. stdlib/ under the current working directory.
  5. stdlib/ in the source file directory or one of its parent directories.

The native build/run driver writes artifacts to INOX_OUTPUT_DIR when set. Otherwise it uses build/inox-artifacts/ relative to the current working directory.

# Windows
$env:INOX_STDLIB = "C:\Tools\inox-windows-x64\stdlib"
$env:INOX_OUTPUT_DIR = "C:\Tools\inox-windows-x64\output"

# Linux
export INOX_STDLIB="$HOME/tools/inox-linux-x64/stdlib"
export INOX_OUTPUT_DIR="$HOME/tools/inox-linux-x64/output"

Lexical rules

Inox is case-insensitive for keywords and identifiers. Documentation uses canonical spelling, but the compiler treats these as equivalent:

PutLn
putln
PUTLN

Inox has 42 reserved words, which never name anything: Use Type Const State Struct Enum if elif else unless while repeat until for in step case try except On do ensure raise retry with mut ref div mod and xor or not shr shl Return pre pos old invariant variant Override.

True, False, Exit, leave, continue, IIf, Fill, bitand, bitor, bitxor and bitnot are predefined names, as Break and Exit in Pascal: they always keep their meaning and can never be declared (a variable, parameter, routine, type or Const named True is an error), but they may name fields and methods (Porta.Exit). Main, Var and Module are ordinary names: the program starts at the routine named Main. Words such as Self, Result and None mean something only where they appear.

{ and } are reserved for a future construct; blocks close with ;.

Line comments use ==:

X := 10  == comment until end of line

String literals use double quotes. Character literals use single quotes. Char is a Unicode scalar value, not a byte and not a grapheme cluster.

Modules and Use

A file is a module, named after the file: Calc.Core.inox (or Calc/Core.inox) is the module Calc.Core, and there is no header. The program's own file may have any name. A file starts with the modules it uses:

Use Std.IO
Use Calc.Core

Main :
    PutLn(Sum(1, 2))        == a routine of Calc.Core
;

Use declares semantic dependencies. It is not textual inclusion and not a C-style #include. Standard modules are resolved through the standard-library search path.

Blocks and statement syntax

Inox uses ; to close blocks. It is not a general statement terminator.

Main :
    if true
        PutLn("yes")
    ;
;

The : has one job: after a routine's name and signature it says "this is a subroutine, and its body starts here". It replaces Pascal's procedure ... begin, Ada's is and C's {, so a routine is written with less than Pascal or Ada and without C's symbols:

Procedure Sum(A : Integer; B : Integer) : Integer;   == Pascal
Begin ... End;

Sum(A Integer, B Integer) Integer :                  == Inox
    Return A + B
;

Nothing else needs it. Control structures such as if, while, repeat, for and with, and the State section, open their body at the line break and close with ;; Type and Const use neither : nor ;. Because : needs a name and a signature before it, a bare : block is a compile error, at any depth. Inox has no anonymous nested blocks:

Main :
    :            == error: a bare ':' block is illegal (CANON-4)
        PutLn(1)
    ;
;

No empty parentheses

Empty parentheses are forbidden for no-argument declarations and no-argument calls.

Correct:

Main :
    PutLn("hello")
;

Account.Print

Incorrect:

Main() :
    PutLn("hello")
;

Account.Print()

Declarations, assignment, and local scope

A typed local declaration introduces a new local symbol:

X Integer := 10

Several names of the same type can be declared on one line. The initializer runs once, and every name starts with that value:

A, B, C Integer := Next(10)   == Next is called once
P, Q TPoint                   == both get the struct defaults

An assignment updates an existing symbol:

X := 20

A local variable that is never read is a compile error. A misspelled name creates a new variable, so the compiler catches the typo. Assigning a variable does not count as reading it:

Counter := 1
Coutner := Counter + 1   == error: local variable never read: Coutner
PutLn(Counter)

Parameters, for iterators, exception bindings, State and Const are exempt.

Module variables live in a State section: no :, the variables on the next lines, and ;:

State
    Counter Integer := 0
    Ready Bool := false
;

Main :
    Counter += 1
    PutLn(Counter, " ", Ready)
;

A module constant is written Const Name := Value and takes the type of its value. It has no written type; to choose one, convert the value:

Const Limit := 10            == Integer
Const Mask := UInt8($FF)     == UInt8
Const Mask UInt8 := $FF      == error: write Const Mask := UInt8($FF)

Compound assignment updates a variable or field in place: Total += I means Total := Total + I. The forms are +=, -=, *=, /= (only where / is valid, so never for Integer) and ^= (power). They cannot be chained, and updating a variable does not count as reading it.

Assignment is a statement, not an expression. It can be chained: the value is computed once and stored from right to left.

A := B := C := Next(10)   == Next is called once
P.X := P.Y := 0

:= cannot appear inside an expression or a condition: X := 2 + (A := 3) and if (A := 3) = 3 are errors. Inside an argument list, Field := Value is only valid in named struct construction, such as TPoint(FX := 10, FY := 20).

These are different operations. A declaration cannot hide an already visible symbol. Shadowing is forbidden.

Invalid:

Main :
    X Integer := 1

    if true
        X Integer := 2
    ;
;

Correct:

Main :
    X Integer := 1

    if true
        X := 2
    ;
;

Symbols declared inside a block are local to that block. Use before declaration is an error.

Functions, subroutines, Return, and Exit

A function has an explicit return type and returns a value with Return Expression:

Add(A Integer, B Integer) Integer :
    Return A + B
;

A subroutine has no return type:

PrintReport :
    PutLn("report")
;

Exit is reserved for early return from subroutines without a value. Functions with a return type must use Return Expression.

Parameters: by value, ref and ref mut

A parameter is normally an immutable copy. Two forms pass a reference to the caller's storage instead:

Sum(ref V Array[1..1000] Integer) Integer :     == read-only, no copy of the array
    Total Integer := 0
    for I in Low(V)..High(V)
        Total += V[I]
    ;
    Return Total
;

Swap(ref mut A Integer, ref mut B Integer) :    == writes the caller's variables
    T Integer := A
    A := B
    B := T
;

A ref parameter cannot be written. A ref mut argument must be a mutable variable, a field or an array element of one (Swap(X, Y), Swap(P.X, Y), Swap(A[1], Y)), never a constant or an expression, and it may not appear in any other argument of the same call: Swap(X, X) and Swap(A[1], A[2]) are compile errors, so a routine never sees one variable through two names. A reference argument has exactly the parameter's type (a Byte variable for a ref mut Byte). A reference lives only during the call: it cannot be stored or returned.

Types and numeric semantics

Hexadecimal literals are written $FF or 0xFF; both mean the same value. An underscore may separate digits: 1_000_000, $FF_FF. A leading zero never means octal: 017 is seventeen.

Current and planned canonical scalar types include Integer, Float, Bool, String, Char, Natural, Currency, and future domain-oriented numeric types.

  • Integer is intended as Int64.
  • Float is intended as Float64. There is no Double.
  • Natural is the non-negative subtype of Integer: 0..Int64.Max, same representation. A Natural can be used wherever an Integer is. As in Ada, storing an Integer into a Natural checks the range by itself, with no conversion written: N += 1 works, and N := N - 5 with N = 3 stops the program with "value out of range for Natural". N Natural := -1 is a compile error.
  • Byte is the same type as UInt8 (0..255). The fixed-width types Int8, Int16, Int32, UInt8, UInt16 and UInt32 never wrap: B += 1 with B = 255 stops the program with "integer overflow". A constant is read in the variable's type when it fits (B Byte := 200, B + 1); B Byte := 256 is a compile error. An Integer variable becomes a Byte only through Byte(X), which checks the range when the program runs.
  • UInt64 (also UInteger) holds 0..18446744073709551615. Its arithmetic never wraps either: 2^64-1 + 1 and 3 - 4 stop the program with "integer overflow", and div, mod, shr and the comparisons are unsigned. A literal above Int64.Max is accepted where a UInt64 is expected (U UInt64 := 18446744073709551615, U = $FFFFFFFFFFFFFFFF, Const Max := UInt64(18446744073709551615)), and only there. A UInt64 and an Integer variable never mix: write U + UInt64(I) or Integer(U) + I, conversions that stop the program when the value does not fit (a negative I, a U above Int64.Max). -U is a compile error; write -Integer(U).
  • There is no Variant or OleVariant: every value has one static type.
  • String is UTF-8, immutable and never null; "" is its default value, not absence. See Strings.
  • Char is a Unicode scalar value.

Integer / is rejected. Use div for integer division and mod for signed remainder. Integer overflow is not a promised wraparound semantic.

Strings

A String holds UTF-8 text and never changes: assigning or passing a String gives a copy of the value, so changing one variable never changes another. Strings work everywhere a value can live: locals, parameters and results, struct fields, array elements, State and ref parameters. A String local or State variable needs an initializer, an array of Strings is filled (Fill("")), and a struct field without default starts as "". = and # compare the bytes.

Type
    TPet Struct
        FName String := "no name"
        FKind String
    ;

Main :
    S String := "abc"
    T := S
    S := "xyz"
    PutLn(S, " ", T, " ", S = T)      == xyz abc false
    P TPet
    Names Array[1..3] String := Fill("")
    Names[2] := P.FName
    PutLn("[", Names[1], "] ", Names[2])  == [] no name
;

Strings are ordered with <, >, <= and >=, as in Pascal: byte by byte, and a String that is the beginning of another comes first. On UTF-8 text this is the order of the Unicode code points, so upper case comes before lower case and accented letters after unaccented ones: "Z" < "a" < "á", "ab" < "abc", "" < "a". It is not the alphabetical order of a language (that will be a library function). The results combine like any Bool:

unless Name >= Limit
    PutLn(Name, " comes before ", Limit)
;
if not (A = B) and (A < C or C = "")
    PutLn("ok")
;

Bool values are ordered as in Pascal and Ada: false < true. Structs are never compared, also as in Pascal: compare their fields.

+ joins Strings and += appends; the String functions (length, slicing, search, case, trimming) come with Use Std.Strings and Use Std.StrUtils, see String functions. Indexing S[I] is reserved: Substr(S, I, 1) gives the character at position I. The compiler frees every String when it is no longer used, also when an exception leaves a routine; there is nothing to free by hand.

Operators and precedence

Precedence follows mathematical convention. Relational operators bind tighter than the logical operators, and bitwise operators bind tighter than the relational ones. Strongest binding first:

LevelOperatorsAssociativity
1call F(X), index A[I]left
2^right
3unary not, -, +, bitnotprefix
4* / div modleft
5+ -left
6shl shrleft
7bitandleft
8bitxorleft
9bitorleft
10.. (range)none
11in (membership)none
12= # < <= > >=left
13andleft
14xorleft
15orleft
16:=right

Inox refuses to guess where the order is commonly misremembered. Mixing different logical operators (A or B and C), different bitwise families (A bitand B bitor C), or a bitwise operator with a shift is a parse error until you add parentheses. .. and in cannot be chained: A..B..C and X in A in B are errors.

B Bool := X in 1..N + 1      == X in (1..(N + 1))
C Bool := X in 1..9 = Flag   == (X in 1..9) = Flag
R Bool := A < B and C < D    == (A < B) and (C < D)

Structs and associated methods

Inox uses structs for data:

Type
    TPoint Struct
        X Integer
        Y Integer
    ;

Associated methods are declared outside the struct. The receiver uses Self; mutable receivers use Self mut:

TPoint.Sum(Self) Integer :
    Return Self.X + Self.Y
;

TPoint.Move(Self mut, DX Integer, DY Integer) :
    Self.X := Self.X + DX
    Self.Y := Self.Y + DY
;

This preserves Object.Method ergonomics without classes or inheritance. Self only reads the receiver: a method that changes it declares Self mut, and is called on something writable (a variable, a field or element of one, a ref mut parameter). A field of a value parameter cannot be assigned either, also inside with.

Fields may have literal defaults, and a field may itself be a struct. A struct declared without := takes its defaults (or zero); named construction builds a value from named fields in any order, and is an expression usable anywhere a value is expected. Structs are values: assignment, parameters and results copy them. Arrays may hold structs:

Type
    TLine Struct
        FA TPoint
        FB TPoint
    ;
    TConfig Struct
        FPort Integer := 8080
        FRate Float := 1.5
        FEnabled Bool := true
    ;

C TConfig                           == FPort 8080, FRate 1.5, FEnabled true
P := TPoint(Y := 2, X := 1)         == named construction, any order
Q TPoint := P                       == a copy
L TLine
L.FB.X := 7                         == field paths reach nested fields
L.FA.Move(1, 1)                     == and methods on them
Points Array[1..10] TPoint := Fill(Q)   == ten copies of Q
Points[3].X := 5

A struct cannot contain itself, directly or through another struct.

A field may be a fixed array, and module State may hold structs and arrays. An array variable is always filled, and copying a struct copies its arrays:

Type
    TBuffer Struct
        FData Array[1..4] Byte := Fill(0)
        FCount Integer := 0
    ;

State
    Origin TPoint := TPoint(X := 1, Y := 2)
    Counts Array[1..3] Integer := Fill(0)
;

B TBuffer
B.FData[2] := 200                   == every index is checked
C TBuffer := B                      == C has its own copy of FData

Explicit initialization cannot be bypassed by putting a value inside a struct, an array or a generic type. A field of an enum, array or type-parameter type has no implicit value: it has a default (a literal, or Fill(Literal) for an array) or is given in the construction, and leaving it out is an error. A struct takes its type defaults (P TPoint, a State variable, New(TPoint)) only when every field has one, nested structs and parts included. Scalar, String, Set and pointer fields without default start at zero, "", empty and None.

Type
    TStatus (Pending, Approved, Rejected)
    TFrame Struct
        FData Array[1..3] Integer      == no default: given in the construction
        FState TStatus                 == no default: given in the construction
        FSize Integer := 0
    ;

F := TFrame(FData := Fill(0), FState := Pending)
G TFrame                               == error: TFrame.FData has no default

A slice cannot be a struct field or a State variable, because it never outlives its array (ADR-0017).

Method reuse: composition without inheritance

A struct can reuse other structs. It lists them after Struct; each one becomes a part, a field named after its type, and its fields and methods are offered directly by the struct, at every level:

Type
    TAddress Struct
        FStreet String := ""
        FCity String := ""
    ;
    TPerson Struct (TAddress)           == reuses TAddress
        FName String := ""
    ;
    TSubscriber Struct (TPerson)        == reuses TPerson, and through it TAddress
        FPlan String := ""
    ;

TAddress.Relocate(Self mut, Street String, City String) :
    Self.FStreet := Street
    Self.FCity := City
;

TPerson.UpdateName(Self mut, Name String) :
    if Name # ""
        Self.FName := Name
    ;
;

S TSubscriber
S.UpdateName("Marcelo")                      == TPerson.UpdateName on the TPerson part of S
S.Relocate("1 Main Street", "Recife")        == two levels down, no forwarding methods
PutLn(S.FName, " ", S.FCity)

The short name is the normal way. The path through the parts (S.TPerson.Title) is needed only to reach a method that an Override replaced, or to use the part itself as a value (Print(S.TPerson)).

A reused method runs on its part: it behaves the same wherever it is reused. A struct may replace a reused method by declaring one with the same name and signature, marked Override; callers of the struct get it, and the part's method stays reachable by its path:

TPerson.Title(Self) String :
    Return "Person"
;
TSubscriber.Title(Self) String Override :
    Return "Subscriber"
;

PutLn(S.Title, " ", S.TPerson.Title)     == Subscriber Person

Nothing is chosen silently. These are errors where the struct is declared: a name reached through two parts (TC Struct (TA, TB) when both have FX), a field of the struct with a reused name, a method with a reused name without Override, an Override that replaces nothing or changes the signature, and reusing something that is not a struct. Two parts with the same method are resolved with an Override in the struct; two parts with the same field, by making one of them a named field. There is no subtyping: a TSubscriber is never passed where a TPerson is expected; S.TPerson is the part. Construction names the part: TSubscriber(TPerson := P, FPlan := "Gold").

A behavior is written once per type, never per value: a thousand soldiers in an Array[1..1000] TSoldier share TSoldier.Run, a TArcher Struct (TSoldier) reuses it without writing it again, and a TKnight may replace it with an Override. Each kind lives in its own array, as in the Entity Component System of modern game engines (examples/reuse-army.inox). One array that mixes archers and knights, where one call runs each element's own version, needs subtyping, which Inox does not have; the future answer is a variant struct, a value that is one of several structs, examined with case (change variant-structs, after enums).

Built-in value types accept methods too, which serve every variable and field of that type (like Delphi helpers). Self is a copy; Self mut is the caller's variable:

String.UpdateStr(Self mut, Value String) :
    if Value # ""
        Self := Value
    ;
;
Integer.Twice(Self) Integer :
    Return Self * 2
;

S.FPlan.UpdateStr("Plan9")
PutLn(S.FPlan, " ", 21.Twice)

A routine with a ref mut parameter works on any field as well: UpdateStr(S.FPlan, "Plan9"), also from a Self mut method (UpdateStr(Self.FName, Name)). examples/method-reuse.inox is a complete program.

Design by contract: pre, pos, invariant

Inox has Eiffel's design by contract (CANON-24). A routine states what the caller must guarantee and what it guarantees in return; a struct states what is always true of its values. The words are pre (Eiffel require), pos (Eiffel ensure; ensure is the cleanup clause of try), old, Result, invariant and variant. They are contextual: outside these places they are ordinary names.

Type
    TStack Struct
        FItems Array[1..5] Integer := Fill(0)
        FCount Integer := 0
        invariant Self.FCount >= 0 and Self.FCount <= 5, "count in range"
    ;

TStack.Push(Self mut, X Integer) :
    pre Self.FCount < 5, "the stack is not full"
    pos Self.FCount = old Self.FCount + 1
    pos Self.FItems[Self.FCount] = X
    Self.FCount += 1
    Self.FItems[Self.FCount] := X
;

TStack.Pop(Self mut) Integer :
    pre Self.FCount > 0
    pos Result = old Self.FItems[Self.FCount]
    X := Self.FItems[Self.FCount]
    Self.FCount -= 1
    Return X
;
  • pre Condition and pos Condition are the first lines of a routine, before any statement; each may end with , "message". Several lines are joined with and.
  • The preconditions are checked on every call, before the body; the postconditions on every normal return. A raised exception leaves without checking them.
  • In a pos, old Expression is the value of the expression on entry, and Result is the value being returned (functions only).
  • A struct's invariant lines go among its fields. The invariant holds after a value is built, before and after every qualified method call (P.Push(1)), after a field is written from outside the struct (P.FCount := 9) and after a call that changes a ref mut argument. Inside the struct's own methods, the calls through bare Self may pass through states that break it.
  • A struct that reuses another (CANON-9) has its parts' invariants too.
  • An Override inherits the contract of the method it replaces. It may weaken the precondition with pre else (the call is accepted if the inherited one or else its own holds) and strengthen the postcondition with pos then (both must hold); a plain pre/pos in an Override is an error.
  • Loops take invariant and, in while and repeat, variant on their first lines. The invariant holds on every iteration and when the loop ends; the variant is an Integer expression that stays non-negative and decreases on every iteration, so the loop ends.
Sum(N Integer) Integer :
    pre N >= 0
    pos Result = N * (N + 1) div 2
    Total := 0
    I := 0
    while I < N
        invariant Total = I * (I + 1) div 2
        variant N - I
        I += 1
        Total += I
    ;
    Return Total
;

A contract only reads: it cannot call a Self mut method, pass a ref mut argument, assign, or use files. A broken contract is a bug, not an exception: the program stops as a runtime trap (exit code 70, CANON-19), like an overflow, and try does not catch it. The message names the clause and the routine:

Inox runtime error: precondition violated: TStack.Push: Self.FCount < 5: the stack is not full

The checks are always on, in every build, through Inox 1.0: no switch turns them off. Eiffel-style monitoring levels, chosen per module (which kinds of contract a module checks), and proving contracts at compile time (as SPARK does) are future work after 1.0. examples/contracts.inox is a complete program.

Safe pointers: Own, Link, New, Free

Inox has pointers without reference counting, without a garbage collector and without null (CANON-25). Every heap object has one owner, Own<T>; everything else that points to it is a Link<T>, which owns nothing and is checked every time it is used. There is no pointer arithmetic and no symbol: the operations are routines, as in Pascal's New, and fields are reached with the dot.

Owners

  • An owner is never copied: Q := P is an error; Q := Move(P) gives the object to Q, and using P afterwards is a compile error until P is assigned again, on every path (branches, loops, handlers).
  • The object is freed by Free(P), when the owner is overwritten, when its routine returns (also through an exception), or when its declaration runs again; the objects it owns are freed with it, in a loop (a list of a million nodes frees without recursion).
  • A value parameter P Own<T> belongs to the routine: the caller writes Move(X) or a new value. A struct holding an owner moves like one.
  • Option<Own<T>> may be None (assigning None frees its object); it is reached through Link(X), which is empty when it is None. An array of owners is Array[...] Option<Own<T>>, filled with Fill(None).

Links

  • Link(X) reaches an owned object, a variable, a field or an element, and goes anywhere: into fields, arrays, results. A Link is copied freely and is born empty.
  • Every use checks a generation stored with the object: when the object was freed, its block reused for another object, or the variable's routine returned, the Link never reaches it. Alive(L) asks; using it stops the program with Inox runtime error: use of a freed object or an empty Link.
  • Same(A, B) asks whether two pointers reach one object; = on pointers is an error; to compare what they reach, compare Value(A) = Value(B) (for numbers, strings and other comparable values) or the fields.
Leak Link<Integer> :
    X Integer := 42
    Return Link(X)            == compiles, as in Pascal
;

Main :
    H := Leak
    PutLn(Alive(H))           == false: X ended with Leak
    PutLn(Value(H))           == stops the program; it never reads the old stack
;

Owners also work with contracts: a pre reads an owner the routine takes, and a pos reads what it held through old P.Field. A Link to a parameter is not supported yet. examples/pointers-tree.inox (a tree of folders whose children are owned and whose parent is a Link) and examples/pointers-navigator.inox (a navigator over an array of records) are complete programs.

Generics: one routine for many types

A routine or a struct may declare type parameters after its name (CANON-8). It is a template: each use with its types makes an instance, checked and compiled like code you wrote for those types, so generics cost nothing at run time.

Type
    TPair<K, V> Struct
        FKey K
        FValue V
    ;

Max<T>(A T, B T) T :
    Return IIf(A > B, A, B)
;

Swap<T>(ref mut A T, ref mut B T) :
    C := A
    A := B
    B := C
;

Zero<T> T :
    Return 0
;

Main :
    P TPair<String, Integer> := TPair(FKey := "one", FValue := 1)
    Q := TPair(FKey := 2.5, FValue := True)       == TPair<Float64, Bool>
    X := 1
    Y := 2
    Swap(X, Y)                                    == Swap<Int64>
    Z Integer := Zero                             == Zero<Int64>, from the target
    PutLn(Max(3, 7), " ", Max("pear", "apple")) == Max<Int64>, Max<String>
    PutLn(P.FKey, " ", Q.FValue, " ", X, " ", Z)            == one true 2 0
;
  • Types are never written in a call. They come from the arguments (a literal takes the type of the others: Max(B, 1) with B Byte is Max<UInt8>), or from the target when the arguments do not fix them. Max<Integer>(3, 7) is an error that says so.
  • No constraints. T may be any type. What the body does with it is checked in each instance: Max on two structs is "in Max<TPoint>, used in Main: structs cannot be compared with '>'". An owner or a File as T works when the body moves it or passes it by ref mut.
  • Generic structs take their types from the written type (TPair<String, Integer>), from the target of a construction or from the values of the fields. A field whose type uses a type parameter (FValue T, FItems Array[1..8] T) never has a default, whatever the instance: D TBox<Integer> is an error, D TBox<Integer> := TBox(FValue := 0) is a value. Their methods are not in the language yet: write a generic routine, Push<T>(ref mut S TStack<T>, X T).

examples/generics.inox builds one stack and uses it for Integers, Strings and pairs.

Control flow

if uses no then and no ::

if X > 0
    PutLn("positive")
elif X < 0
    PutLn("negative")
else
    PutLn("zero")
;

while uses no do and no ::

while X > 0
    X := X - 1
;

repeat is flexible; until is an internal conditional exit:

repeat
    PutLn(X)
    X := X + 1
until X > 10
;

for ranges are inclusive. The iterator is implicit, read-only, local to the loop body, and cannot shadow a visible symbol:

for I in 1..10
    PutLn(I)
;

for I in 10..1 step 2
    PutLn(I)
;

for I in 1..N + 1 step 3
    PutLn(I)
;

The step is written with step and must be positive; the direction comes from the bounds. The old form for I in A..B (S) is an error.

Sequential loops may reuse the same iterator name because their scopes do not overlap.

leave exits the nearest enclosing loop; continue proceeds to its next iteration. Both are valid only inside a loop:

while true
    X := X + 1
    if X > 10
        leave
    ;
;

Block structures nest recursively whenever the combination is semantically valid: loops inside loops, if/elif/else inside loop bodies, try inside loops, and so on. leave and continue always act on the nearest loop; until may appear anywhere in a repeat body, also inside if, try or a loop nested in the repeat, and exits the nearest repeat:

for I in 1..3
    R := 0
    repeat
        R := R + 1
        if R = I
            until true
        ;
    ;
    for J in 1..3
        if J = 2
            continue
        elif J > I
            leave
        else
            PutLn(I, " ", J)
        ;
    ;
;

Constructs the semantic analyzer accepts but the LLVM backend does not lower yet are reported as “not yet implemented in the LLVM backend” and are measured in docs/BACKEND_GAPS.md.

Conditional expression

IIf(Condition, A, B) selects a value. Each branch is an expression, never a block, and only the chosen branch is evaluated (unlike the IIf of Visual Basic, which evaluates both). Chains nest:

Max := IIf(A > B, A, B)
Fee := IIf(Age >= 60, 0.5, 1.0)
Band := IIf(N < 10, "low", IIf(N < 100, "medium", "high"))

The if statement keeps its own form, without then.

case

case follows Ada/SPARK, adapted to Inox. Alternatives are separated by |. A choice is a constant value or a constant range A..B. Choices may not overlap, and there is no fall-through:

case Value
    1 | 2
        PutLn("small")
    3..9
        PutLn("medium")
    10 | 20..29 | 40 PutLn("mixed")
    else
        PutLn("other")
;

The last arm, else, is required unless the choices cover every value of the selector type (it was spelled otherwise until canon revision 3.74). A Bool case that handles True and False needs no else. A case on an Integer code that handles only 404 is rejected. The selector must be discrete: an integer type, Char, Bool, an enum or a range.

with

with Target opens a block where .Member is a member of the target, as in Visual Basic; names without the dot follow the normal scope. Assignment is :=, as everywhere (= compares).

with Customer
    .Name := "Coho Vineyard"
    .City := "Redmond"
;

with Customer.Comments
    .Add("First comment.")
    Pause
    .Add("Second comment.")
;

The target is any variable or value: a field, an array element, a ref mut parameter, State, or an object reached through Own or Link. It is evaluated once, on entry: in with A[I] the element stays the same even if I changes in the body, and a call in the index runs once. Every .Member acts on that storage, never on a copy. Through a pointer, every .Member checks that the object still exists, so a Free inside the body stops the program at the next use. A type is not a target: to build a value, write C := TCustomer(Name := "...").

Exceptions

Inox provides structured exception handling with try, except, typed On handlers, optional Else, ensure, Raise, and bounded Retry(N). Typed handlers are tested in source order; Else is the catch-all after them. A plain except is itself a catch-all.

try
    RiskyOperation
except
    On RangeError
        PutLn("range failure")
    ;

    On E IOError
        PutLn("I/O failure")
        Retry(3)
    ;

    Else
        PutLn("other exception")
    ;
ensure
    Cleanup
;

Raise ExceptionType raises a new exception. A bare Raise inside a handler rethrows the exception currently being handled. Retry(N) is valid only in an explicit On/Else handler and permits at most N additional executions of the associated try body. If the budget is exhausted, the current exception is rethrown. When an ensure is present, it runs before each retry.

ensure executes on normal and exceptional departure, including supported nonlocal control transfers such as Return, Exit, and loop control crossing the construct. A try must contain at least except or ensure.

Since canon revision 3.20, leave and ensure are keywords; the former break and finally are ordinary identifiers.

The implementation (canon revision 3.17) models the standard exception taxonomy as nominal exception types (for example FileNotFound is a subtype-category match of IOError) while the minimal libinoxrt remains a generic transport/unwind runtime using opaque type identifiers. User-defined exception declaration syntax and payload reflection remain deferred; the language rules are defined in the constitution (CANON-15).

Std.IO and variadic output

Put and PutLn accept one or more arguments. Arguments are emitted sequentially; this is not string concatenation and does not allocate a combined intermediate string. PutLn appends exactly one newline after the final argument.

Put("J=", J)
PutLn("Cycle number ", J)
PutLn("A", 10, "B", true)

GetLn(S) with a String variable reads the rest of the input line into S, without the line break (a carriage return before it is dropped too). At the end of the input S is "". The line must be valid UTF-8; otherwise the program stops with "invalid UTF-8 input". Get reads Integer values only.

Main :
    Name String := ""
    Put("Name: ")
    GetLn(Name)
    PutLn("Hello, ", Name)
;

The current backend lowers these facilities through the runtime/compiler path used by the LLVM smoke-test backend. This is not the final language ABI.

String functions: Std.Strings and Std.StrUtils

+ joins two Strings and += appends, with no Use. There is no implicit conversion: "N=" + N with an Integer N is an error, and PutLn("N=", N) prints both without building a String. A chain such as A + " " + B + "!" makes one String in one step, and S += X (or S := S + X) writes X at the end of S in place when no other variable holds the same text, so a loop of appends takes linear time, as with a string builder. A copy taken before the append keeps its value.

Use Std.Strings gives the functions nearly every program needs; Use Std.StrUtils adds the conveniences, in the style of Delphi, and gives everything of Std.Strings. Without the Use, the names are free for your own routines.

== Counts the words of S, separated by single spaces.
Words(S String) Integer :
    Text := Trim(S)
    if Text = ""
        Return 0
    ;
    Count := 1
    Rest := Text
    P := Position(" ", Rest)
    while P > 0
        Count += 1
        Rest := Substr(Rest, P + 1, Length(Rest) - P)
        P := Position(" ", Rest)
    ;
    Return Count
;

Text files: Std.Files and Std.IOUtils

Use Std.Files gives a program the type File and the basic operations: OpenRead, Create, OpenAppend, ReadLn, Eof, Write, WriteLn and Close. Use Std.IOUtils adds the conveniences Exists, DeleteFile and RenameFile, and gives everything of Std.Files. Without them, names such as Create, Close or Exists are free for your own routines.

A file closes itself when the routine that holds it ends, by any path: the end, Return, Exit or an exception. Storing a new file in a File variable closes the old one. A file declared inside a loop is closed when the next round opens another, and the last one when the routine ends; close a file yourself before deleting or renaming it, because Windows refuses to delete an open file.

A File is never copied. It lives in a local variable that receives a file just opened, or in a ref mut parameter; G := F, a File field, array element, State variable or result are compile errors:

AddLines(ref mut Target File, Count Integer) :
    for I in 1..Count
        WriteLn(Target, "line ", I)
    ;
;

Text is UTF-8. Lines are written with "\n" on every system and read with "\n" or "\r\n". Every failure is an ordinary exception: FileNotFound, PermissionDenied, AlreadyExists, DiskFull, or IOError (their parent, also raised for a closed file, invalid UTF-8, or reading a file opened for writing):

try
    F := OpenRead(Path)
    PutLn(ReadLn(F))
except
    On FileNotFound
        G := Create(Path)
        WriteLn(G, "created")
        Close(G)
        Retry(1)
    ;
ensure
    PutLn("done")
;

A complete tour, with every operation and every error handled with try, is examples/file_io.inox (the test suite runs it, like every example, and checks its output). Binary files, positions and streams are not in the language yet: their design is the OpenSpec change binary-streams, awaiting approval.

Arrays, vectors, ranges, enums, and sets

The 0.1 direction defines or reserves several Pascal/Ada-inspired aggregate concepts:

  • Fixed arrays use explicit ranges: Array[Low..High] Type. They work today:
Const Size := 5

Sum(V Array[1..Size] Integer) Integer :
    Total Integer := 0
    for I in Low(V)..High(V)
        Total += V[I]
    ;
    Return Total
;

Main :
    A Array[1..Size] Integer := Fill(0)
    for I in 1..Size
        A[I] := I * I
    ;
    A[2] += 100
    PutLn(Sum(A))
    M Array[1..2, -1..1] Byte := Fill(0)
    M[1, 0] := 200
;

A slice is a read-only view of part of an array, without copying: A[3..6], A[..3], A[7..], A[..]. Its type is Slice<Integer>, and it keeps the array's indices (A[3..6] is indexed 3 to 6; Low, High and Length give its bounds):

Sum(S Slice<Integer>) Integer :
    Total Integer := 0
    for I in Low(S)..High(S)
        Total += S[I]
    ;
    Return Total
;

PutLn(Sum(A[2..4]), " ", Sum(A[..]))

A slice is never empty, cannot be written, is bound once and cannot be returned, so it never outlives its array; bounds outside the array stop the program with "slice bounds out of range".

Every array is initialized where it is declared, whatever its element type: no element is ever an implicit zero, False or first enum literal. Fill(Value) is the array its target expects, with the target's type and bounds, every element a copy of Value, evaluated once, as Ada's (others => Value) and Rust's [Value; N] without repeating the size. It is written wherever an array is expected (a declaration, a State initializer, an assignment, an argument, a Return); in two dimensions Value is an element or a whole row:

Counts Array[1..100] Integer := Fill(0)
Hand Array[1..5] TSuit := Fill(Club)
Names Array[1..3] String := Fill("")
Zero TPoint
Points Array[1..10] TPoint := Fill(Zero)
Row Array[1..4] Byte := Fill(1)
Grid Array[1..3, 1..4] Byte := Fill(Row)
Counts := Fill(-1)

An array of a Range checks the value (Fill(13) into an Array[...] TMonth stops the program with "value out of range"), each String element holds its own copy, and an array of owners is filled only with None. Array literals, with one value per element, are reserved for later.

An array is a value: assigning it (B Array[1..Size] Integer := A) or passing it to a routine copies it. Every index is checked: A[I] with I outside Low(A)..High(A) stops the program with "array index out of bounds", and a constant index outside the bounds is a compile error. Low, High and Length are constants. A multi-dimensional array is an array of arrays (M[I, J] is M[I][J]). Bounds are integer literals or Consts; elements are integers, Float or Bool for now.

  • Vectors are planned as dynamic, 0-based, bounds-checked collections.
  • Generic types are written with angle brackets: Vector<Integer>, Set<TCardSuit>. Square brackets stay for indexing and bounds: Values[I], Array[1..10] Integer. The generic structs of a program are written the same way (Generics); Vector and Set are not built in yet.

Enums, Ranges and Sets work today; see Enums, ranges and sets. Vectors are language direction, not yet implemented.

Enums, ranges and sets

An enum names a few values: short, TSuit (Club, Diamond, Heart, Spade), or one literal per line between TDay Enum and ;. It is never an Integer: Ord(Heart) is 2, TSuit(I) converts back and stops the program with "integer conversion out of range" when I is not 0..3, and Heart + 1 is an error; Succ and Pred step to the next and previous literal and stop the program past the ends. Values of one enum compare by order (Club < Spade), Low(TSuit) and High(TSuit) are the first and last literal, for S in Diamond..Spade walks them, and PutLn(S) prints the literal's name as declared. A literal belongs to one enum only. An enum variable needs an initializer; a struct field may default to a literal, and one without a default or an array element starts at the first literal.

A Range, TScore Range 0..100, is an Integer that never leaves its bounds: storing a value outside them stops the program with "value out of range", and a constant outside them is a compile error. Its arithmetic is Integer arithmetic, so Total := Total + 11 is checked only when it is stored. A case on an enum or a Range without else must cover every value, and the error names the first one missing:

Type
    TSuit (Club, Diamond, Heart, Spade)
    TRank (Two, Three, Four, Five, Six, Seven, Eight, Nine, Ten, Jack, Queen, King, Ace)
    TScore Range 0..100
    TCard Struct
        FSuit TSuit := Club
        FRank TRank := Two
    ;

Points(R TRank) Integer :
    case R
        Two..Ten
            Return Ord(R) + 2
        Jack | Queen | King
            Return 10
        Ace
            Return 11
    ;
;

Color(S TSuit) String :
    case S
        Club | Spade
            Return "black"
        Diamond | Heart
            Return "red"
    ;
;

A Set, Set<TSuit>, is a set over an enum or a Range of at most 256 values, a value that starts empty. [Club, Heart] writes one where a Set is expected; X in S tests membership; = and # compare, <= and >= test subset and superset; Union, Intersection, Difference, SymmetricDifference, Include(S, X) and Exclude(S, X) return new sets. Unlike Pascal's Include and Exclude, they never change their argument: write S := Include(S, Heart); a call that drops the new set is an error that says so. It costs one bit per value, with no allocation. X in A..B also tests a value against two bounds.

examples/cards.inox scores a hand of cards with all three. A Range over Char (TLetter Range 'A'..'Z') is declared and waits for Char values.

Runtime and implementation status

Inox does not yet provide a complete standalone language runtime. The stdlib/Std.*.inox files remain early standard-library modules and documentation anchors. The minimal static libinoxrt component (canon revision 3.17) provides exception transport and unwinding; since revision 3.55 it also holds the String runtime (reference-counted immutable blocks and line input), and since revision 3.59 the text-file runtime. It is not yet a general-purpose language runtime or RTTI system.

The current compiler executable is a native C++ program. The native build/run path emits textual LLVM IR and delegates final executable generation to external Clang. Modules that use exception handling or Strings are linked through clang++ together with libinoxrt; other modules retain the existing Clang path.

Design stance

Inox rejects unsafe defaults:

  • universal null;
  • implicit narrowing;
  • integer wraparound guarantees;
  • unchecked bounds;
  • implicit aliasing;
  • classes;
  • inheritance;
  • Java-style interfaces.

Behavior is reused by method reuse, not by traits, protocols or interfaces. Future work includes modules, vectors, sets, arenas, borrowing, unsafe boundaries, and structured parallelism.
